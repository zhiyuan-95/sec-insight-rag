Plan 202 - Metric-First Missing Coverage Resolution

## Purpose

Plan 202 handles internal financial metrics after the mapping pipeline has
collected all available target-coverage evidence:

1. hard mapping from source-controlled and approved mappings
2. approved alternate SEC/XBRL concepts for the same business metric
3. semantic candidate discovery and review evidence
4. optional formula and zero-target diagnostics from present raw concepts

The purpose is not to force every missing target concept into a value. The
purpose is to collapse tag-level evidence into one metric-level review surface.
For each unresolved internal metric, the report should let an LLM or reviewer
choose one of the available paths:

1. use a semantic candidate generated by round two
2. compose a formula from the provided raw concepts
3. treat the missing target as zero when there is affirmative same-context
   evidence

If none of those paths has evidence, the metric stays unavailable.

Formula and zero-target outputs are review evidence. They are not approved
mappings, reported facts, deterministic calculations, or indicator inputs.

## Current Scope

Current implementation scope:

```text
Metric-first review surface for internal metrics after target coverage,
approved alternates, semantic candidates, and formula/zero diagnostics.
```

The current scope includes:

- one metric-level coverage resolution row per internal metric
- direct mapped and approved-alternate metrics marked as already covered
- unresolved metrics marked for `llm_choose_mapping_formula_or_zero`
- LLM/reviewer option sets drawn from available evidence:
  `semantic_candidate`, `formula_from_raw_concepts`, and `zero_target`
- period-scoped eligible raw fact pools
- statement-first formula proposal prompts
- exact context-hash cache reuse across future runs
- deterministic validation of generated or reused proposals
- MS200 report diagnostics
- focused automated tests and docs updates

The current scope does not include:

- durable recovered metric storage
- recovered rows in `financial_metrics`
- database schema changes
- indicator consumption of recovered values
- accounting identity residual inference
- automatic approval from model confidence or model agreement
- automatic approval from semantic similarity score
- fuzzy or near-match formula cache reuse
- a third local Hugging Face formula provider

LLM outputs and reviewer choice options are review evidence. They are not
approved mappings, reported facts, deterministic calculations, or indicator
inputs.

## Evidence Boundaries

Keep these evidence layers separate:

```text
raw_xbrl_facts
  canonical archive of observed SEC/XBRL facts

financial_metrics
  curated one-raw-fact base metrics

formula proposal diagnostics
  report-only LLM recommendations and deterministic validation results

metric coverage resolution
  one metric-level packet combining target coverage, approved alternates,
  semantic candidates, formula evidence, and zero evidence

financial_indicators
  deterministic outputs from approved metric inputs
```

Do not present calculated or proposed values as reported facts. Do not present
LLM reasoning as deterministic financial analysis.

## Metric-First Algorithm

For each internal metric in the target coverage catalog:

1. Build target-tag coverage after source-controlled mappings and approved
   learned mappings.
2. Mark metrics covered by direct mapped target tags as `mapped`.
3. Mark metrics covered by approved alternate tags as
   `covered_by_approved_alternate`.
4. Keep semantic candidates from round two as review-only candidates.
5. Optionally generate formula and zero-target diagnostics from raw facts that
   exist in comparable accounting contexts.
6. Call `src/processing/metric_coverage.py` to collapse tag-level evidence into
   one row per internal metric.
7. For unresolved metrics with review evidence, set:
   - `coverage_status`: `needs_llm_resolution`
   - `reviewer_action`: `llm_choose_mapping_formula_or_zero`
   - `llm_choice_options`: the available subset of `semantic_candidate`,
     `formula_from_raw_concepts`, and `zero_target`
8. For unresolved metrics with no review evidence, set:
   - `coverage_status`: `no_evidence`
   - `reviewer_action`: `no_evidence_to_review`
9. Render the metric-first rows before target-level concept coverage in the
   MS200 report.

The resolver must not approve mappings, persist recovered values, or feed
indicators.

## Formula And Zero Diagnostics

For each missing target concept that needs raw-concept evidence after direct
coverage, approved alternate coverage, and semantic candidate discovery:

1. Select unresolved target concepts after the earlier mapping evidence stages.
2. Build period-scoped raw fact pools from `raw_xbrl_facts`.
3. Classify concepts by accounting structure:
   - `same_statement_candidates`
   - `unclassified_same_period_candidates`
   - `cross_statement_candidates`
4. Compute an exact formula context fingerprint.
5. Reuse a cached proposal only when the fingerprint is an exact match.
6. On cache miss, call each configured provider once for that formula context.
7. Require one best formula proposal, one evidence-backed zero-target decision,
   or a structured `no_formula` decision.
8. Validate generated or reused proposals against current-period raw facts.
9. Feed the diagnostics into the metric-first coverage resolver.
10. Render proposal, cache, component, and validation evidence in the MS200
   report.

Currently implemented formula proposal provider panel:

```text
gemini-2.5-flash
OpenAI configured structured-output model, defaulting to gpt-4.1-mini
```

Llama-Open-Finance-8B is deferred. It should not be presented as a currently
configured provider until there is source code and configuration for it.

## Period-Scoped Fact Pools

Do not send every raw concept for the company across all filings and periods to
the LLM.

A formula proposal input must use one comparable accounting context. The period
scope should include, where available:

- accession number or compatible filing context
- fiscal year
- fiscal period
- period type
- unit
- start date and end date, or instant date
- consolidated/company-level status when available

Balance sheet targets usually use instant/end-date contexts. Income statement
and cash flow targets usually use duration/start-end contexts.

If the system cannot form a usable same-period pool, report `no_eligible_period_pool`
instead of forcing a formula request.

## Statement-First Prompting

The prompt must clearly state the target primary statement:

```text
balance_sheet
income_statement
cash_flow_statement
unknown_statement
```

The LLM must:

- first try same-statement concepts
- use unclassified same-period concepts only when accounting logic supports it
- use cross-statement concepts only if no credible same-statement solution
  exists
- explain every cross-statement component
- use XBRL calculation or presentation relationships only when supplied by the
  system
- otherwise cite common US GAAP presentation logic and state that filing-level
  relationship evidence was not provided

The LLM must not:

- invent concepts, values, units, or facts
- use the missing target itself as a component
- approve mappings
- write values to durable metric storage
- infer zero only because the target fact is missing

## Formula Proposal Cache

Persist generated formula proposals as local generated review evidence under:

```text
data_store/knowledge/formula_proposals/
```

This cache is not `financial_metrics`, not approved mapping state, and not a
source of reported facts. It exists to avoid repeated provider calls when the
same accounting context appears again.

Exact context fingerprint should include:

- target metric name
- target XBRL concept
- target primary statement
- target catalog version
- prompt version
- provider name
- model name
- cache schema version
- formula context fingerprint version
- statement bucket classifier version
- normalized same-statement taxonomy:concept list
- normalized unclassified same-period taxonomy:concept list
- normalized cross-statement taxonomy:concept list
- unit
- period type
- taxonomy namespace or taxonomy version, when available
- issuer-extension label/documentation hash, when available
- relationship evidence version, when available

Exact context fingerprint should not include:

- numeric values
- raw fact IDs
- accession number
- filing date
- fiscal year
- fiscal period

Those fields vary across periods or filings, but the accounting formula may be
the same. The current period still controls validation and report evidence.

Cache safety rules:

- cache only parsed `proposed`, `target_zero`, and structured `no_formula`
  responses
- do not cache `provider_unavailable` or `provider_failed`
- treat corrupt or schema-incompatible cache entries as warning-level misses
- write cache entries atomically
- require exact context match for reuse
- revalidate every reused proposal against the current period
- report cache status in diagnostics

Cache statuses:

```text
generated_new
reused_exact_context
reused_but_validation_failed
cache_unavailable
cache_entry_invalid
```

## Deterministic Validation

Validation must reject:

- component outside the eligible period-scoped raw fact pool
- component from incompatible period context
- circular use of the missing target
- missing numeric values
- incompatible unit
- incompatible period type
- incompatible fiscal period or date window
- duplicate ambiguous same-period component facts
- cross-statement component without explanation

Validation may accept a formula only when all components exist in the current
period pool and share an unambiguous compatible context.

Model confidence and model agreement remain review signals only.

## Report Output Contract

The MS200 report should show `Metric-First Coverage Resolution` before the
target-level concept coverage sections. Each metric-first row should show:

- internal metric name
- statement type
- coverage status
- reviewer action
- LLM choice options
- target XBRL concepts
- mapped target concepts
- approved alternate concepts
- semantic candidates
- formula evidence counts
- zero evidence counts
- notes

The formula proposal diagnostics should show:

- missing target metric and XBRL concept
- target primary statement
- provider and model
- prompt version
- formula context fingerprint or short hash
- formula proposal period context
- cache status
- formula expression or `no_formula`
- confidence
- reason and uncertainty
- component concepts
- component statement relationship
- component mapping status:
  - found target
  - mapped base metric
  - approved alternate
  - unknown/unmapped
- source raw fact IDs or representative raw fact IDs
- deterministic validation status
- skip reason or warning
- provider failure or cache warning, if any
- model agreement label
- cache hit/miss counts

The report should remain evidence-first. It should not call the result pass or
fail.

## Tests

Focused automated tests should cover:

Metric-first coverage resolution:

- direct mapped target rows produce `mapped` with no LLM choice
- approved alternate rows produce `covered_by_approved_alternate`
- semantic candidates, formula diagnostics, and zero diagnostics produce
  `needs_llm_resolution`
- LLM choice options are limited to the available evidence
- no-evidence rows produce `no_evidence_to_review`
- metric-first report rows include semantic, formula, and zero evidence fields

Formula context construction:

- period-scoped pools exclude incompatible periods
- target primary statement is included
- same-statement, unclassified, and cross-statement buckets are deterministic
- prompt payload does not contain broad cross-period concept pools

Context fingerprint and cache:

- same concept set with changed numeric values reuses cache
- same concept set with changed raw fact IDs reuses cache
- changed concept set misses cache
- changed target, statement, unit, or period type misses cache
- changed prompt version, provider, or model misses cache
- changed target catalog, classifier, relationship evidence, or extension
  metadata version misses cache
- provider failures are not cached
- corrupt cache entries become report warnings and cache misses
- structured `no_formula` decisions reuse only on exact context match
- reused proposals are revalidated for the current period

Validation:

- outside-pool component rejected
- incompatible-period component rejected
- circular target component rejected
- duplicate same-period component facts rejected
- unit mismatch rejected
- period mismatch rejected
- cross-statement component without explanation rejected
- model confidence and model consensus remain review-only

Report rendering:

- formula proposal diagnostics section appears
- period context appears
- target primary statement appears
- statement relationship appears for components
- cache status appears
- cache hit/miss counts appear
- provider failures and cache warnings appear
- no recovered rows are inserted into `financial_metrics`

## Deferred Tracks

These are explicitly not part of the current implementation.

Durable recovered metric storage:

- Requires explicit user approval.
- Should not overload `financial_metrics`.
- Prefer a separate recovered metric layer with formula version, source raw fact
  IDs, source accessions, validation status, and review decision.

Debt component recovery:

- Existing debt examples remain useful background.
- Optional-zero behavior must be formula-controlled and supported by coverage
  proof.
- Do not treat missing components as zero globally.

Accounting identity inference:

- Requires explicit user approval.
- Only possible for one-unknown cases with compatible totals and sibling
  components.
- Must not distribute residual value across multiple unknowns.

Indicator integration:

- Requires durable recovered metric provenance first.
- Indicator reports must expose direct facts, recovered values, assumed-zero
  components, and formula versions distinctly.

Human or policy approval:

- Similarity scores retrieve candidates; they do not approve mappings.
- LLM confidence and agreement are evidence; they do not approve mappings.
- Any durable use requires deterministic validation and an explicit approval
  policy.
- A metric-first LLM/reviewer choice is still not durable use unless a separate
  reviewed decision type is added.

## Success Criteria

Plan 202 succeeds when:

- direct mapped metrics are marked covered without an LLM choice
- approved alternate metrics are marked covered without an LLM choice
- unresolved metrics expose `llm_choose_mapping_formula_or_zero` only when
  semantic, formula, or zero evidence exists
- LLM choice options are limited to the evidence actually available for the
  metric
- LLM formula proposal inputs are scoped to one comparable period/context
- prompts state the target primary statement
- same-statement concepts are tried before cross-statement concepts
- cross-statement components require accounting explanation
- exact-context formula proposal cache reuse avoids repeated provider calls
- reused proposals are revalidated against current-period raw facts
- provider failures and cache issues are visible in the report
- formula proposals remain review-only
- zero-target proposals require affirmative evidence and remain review-only
- no recovered values are inserted into `financial_metrics`
- downstream indicators do not consume recovered values
- MS200 reports include `Metric-First Coverage Resolution`
- MS200 report explains proposal, component, period, statement, cache, and
  validation evidence clearly enough for manual review
