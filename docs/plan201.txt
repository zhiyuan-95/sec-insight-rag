Plan 201 - Gemini-Assisted Industry Label XBRL Concept Mapping

Problem Summary

The problem is that different industries need different financial metrics, and
those metrics may come from different SEC/XBRL raw facts. Even when two
companies are talking about the same business idea, their filings may use
different XBRL concepts, different wording, or industry-specific tags.

A single global concept-to-metric mapping is not enough long term. But mapping
every unknown XBRL concept into financial_metrics is also wrong, because many
SEC companyfacts concepts are disclosures, rollforwards, notes, tax details,
registration facts, segment facts, or company-specific tags that should remain
raw evidence.

The system needs a way to:

- keep the raw XBRL archive broad
- classify each company into one or more approved hard industry labels from
  the latest relevant 10-K Item 1 Business section
- reuse approved labels during the same annual filing cycle
- refresh the labels when a newer 10-K is ingested, because a company can move
  into or out of industries over time
- define target XBRL concept sets for each hard industry label
- use the union of target XBRL concept sets when a company has multiple hard industry labels
- map only approved, business-meaningful concepts into financial_metrics
- persist the approved company concept profile so later ingestions can reuse
  reviewed concept mappings without rerunning semantic mapping every time
- keep unknown concepts visible for review
- run semantic mapping only after Round 1 hard mapping leaves missing target
  XBRL concepts
- show the industry-label target XBRL concepts and mapping coverage in the experiment
  report

The key rule:

```text
Hard industry label target XBRL concept sets guide mapping and reporting.
They do not limit raw XBRL ingestion.
```

Second key rule:

```text
Approved company concept profiles speed up later mapping.
They do not limit raw XBRL ingestion.
```

Source-of-truth note:

```text
common language.md
  owns mapping terminology.

src/processing/mapping_catalog.py
  owns executable hard-mapping candidates used by the system.

xbrl_direct_candidate_mapping.txt
  owns research candidates and candidate-expansion notes, including candidate
  concepts that may require review before becoming hard mappings.

plan201.txt
  owns design intent and implementation phases. It should not duplicate the
  complete live candidate catalog.
```

Hard Industry Label Requirement

Plan 201 must add a hard industry label system.

Every company must be assigned one or more hard industry labels from this fixed
industry label set:

```text
Energy
Materials
Industrials
Consumer Discretionary
Consumer Staples
Health Care
Financials
Information Technology
Communication Services
Utilities
Real Estate
```

There are no secondary labels in Plan 201.

If a company has business in multiple industries, the company should receive
multiple hard industry labels. The target XBRL concept set for that company is
the union of the common base concepts and the target concepts for all assigned
hard industry labels.

Rule:

```text
company_hard_industry_labels:
  one or more labels from the fixed 11-label set

target XBRL concept set:
  common base candidate XBRL concepts
  UNION candidate XBRL concepts for every assigned hard industry label
```

The 11-label set is intended to cover all public market companies. If the system
cannot confidently assign any label, that is a data quality/review state, not a
new industry label.

Company Industry Label Assignment Requirement

Plan 201 must make hard industry label assignment explicit and auditable.

Company hard industry labels should be stored in the system as reusable company
state. The stored approved labels are the labels that control target XBRL
concept selection.

The label lifecycle is:

```text
first company initialization:
  no approved labels exist
  -> use latest active 10-K
  -> extract Item 1. Business
  -> classify with Gemini using the fixed 11-label set
  -> validate strict JSON output
  -> if confidence and evidence pass the gate:
       persist labels as approved
       use labels for target XBRL concept selection
     else:
       persist review-needed evidence
       use common-base targets only

normal reuse during the same annual filing cycle:
  approved labels exist for the current latest 10-K
  -> reuse stored labels
  -> do not call Gemini

new annual 10-K ingested:
  latest 10-K accession changed
  -> extract new Item 1. Business
  -> classify again with Gemini
  -> if confidence and evidence pass:
       replace/update approved labels
     else:
       keep prior approved labels for continuity and report the refresh failure
       as a review state
```

Important meaning:

```text
No approved labels means:
  no rows in company_industry_labels for this company have status = approved
  for the latest accepted classification state.

It does not mean the company has no industry.
```

Recommended first file:

```text
src/processing/company_industry_labels.py
```

Each assignment should store:

```text
CompanyIndustryLabelAssignment
  ticker
  cik
  assigned_industry_labels
  assignment_source
  assignment_reason
  supporting_evidence
  source_form
  source_accession_number
  source_filing_date
  source_section
  source_text_sha256
  classifier_model
  classifier_prompt_version
  confidence
  reviewed_at
  label_status
  notes
```

Storage note:

Use the existing `company_industry_labels` table first. Store classifier
metadata such as source accession, source section, prompt version, source text
hash, and evidence quotes inside `evidence_json` unless later reporting needs
prove that dedicated columns are required. Do not change the schema just to
mirror the plan vocabulary.

Rules:

- `assigned_industry_labels` must use only the fixed 11-label set.
- A company can have more than one hard industry label.
- `assignment_source` should show whether the label came from Gemini
  classification, manual review, source-controlled seed data, SIC support, or
  another approved source.
- SIC code, SIC description, observed XBRL concepts, and business descriptions
  are supporting evidence. Observed XBRL concepts must not be the source of
  truth for labels.
- Gemini must classify from SEC filing narrative evidence, specifically the
  latest relevant 10-K Item 1 Business section.
- Gemini output must be strict JSON, not free-form text.
- The JSON must include `industry_labels`, `confidence`, `reason`, and
  `evidence_quotes`.
- The system must validate every returned label against the fixed 11-label set.
- High-confidence, valid output can be persisted as `approved`.
- Low-confidence, malformed, or invalid output must be persisted as
  `needs_label_review` evidence and must not control industry-specific target
  XBRL concept selection.
- Approved labels should be reused until a newer 10-K is ingested.
- A newer 10-K should trigger annual reclassification because company business
  mix can change.
- If no label is assigned, the report should mark the company as
  `needs_label_review` and avoid pretending that industry-specific target XBRL
  concept coverage is complete.

Important:

Do not let observed XBRL concepts alone assign the industry label. That creates
circular logic:

```text
observed raw facts
  -> inferred label
  -> expected XBRL concepts
```

Observed XBRL concept patterns can help review an assignment, but they should not
silently decide the assignment.

Gemini classification is allowed for industry labels only. Gemini must not
approve raw XBRL concept-to-financial metric mappings. Raw concept mappings
still require deterministic catalog entries or governed approved mapping records.

Industry Target Concept Catalog Requirement

Plan 201 must keep an inspectable catalog of hard industry labels and their
target SEC/XBRL concepts.

Important:

This catalog is not a list of every raw XBRL concept in SEC companyfacts. It is
the source-controlled list of concepts that the system intentionally looks for
because they may map to system financial metrics or support indicators.

Authoritative files:

```text
src/processing/mapping_catalog.py
  executable catalog used by ingestion, base metric mapping, semantic mapping,
  and MS200 coverage reporting.

xbrl_direct_candidate_mapping.txt
  research and expansion notes for direct candidates, broader candidates,
  company-extension patterns, and concepts that require review before hard
  mapping.

tests/test_mapping_catalog.py
  regression tests proving important candidates stay available and correctly
  scoped.
```

Do not keep a second complete candidate list in this plan. The plan should
describe catalog rules and cite the source files above. The executable catalog
must remain the source of truth.

Current catalog rules:

```text
common base targets:
  target XBRL concepts used by most companies and core indicators

industry targets:
  additional target XBRL concepts used only when a company has a matching hard
  industry label

compatibility targets:
  deterministic mappings preserved for current behavior even when target
  coverage treats the concept as industry-specific

research candidates:
  concepts or company-extension patterns tracked in
  xbrl_direct_candidate_mapping.txt but not automatically promoted into hard
  mapping
```

Examples of current common-base candidate groups:

```text
revenue:
  RevenueFromContractWithCustomerExcludingAssessedTax
  RevenueFromContractWithCustomerIncludingAssessedTax
  Revenues
  SalesRevenueNet

net_income:
  NetIncomeLoss
  ProfitLoss

interest_expense:
  InterestExpenseNonOperating
  InterestExpenseNonoperating
  InterestExpense
  InterestAndDebtExpense

short_term_investments:
  ShortTermInvestments
  MarketableSecuritiesCurrent
  AvailableForSaleSecuritiesCurrent
  TradingSecuritiesCurrent
  HeldToMaturitySecuritiesCurrent
  OtherShortTermInvestments
  InvestmentsCurrent

capital_expenditure:
  PaymentsToAcquirePropertyPlantAndEquipment
  PaymentsToAcquireProductiveAssets

depreciation_and_amortization:
  DepreciationDepletionAndAmortization
  DepreciationDepletionAndAmortizationExpense
  DepreciationAndAmortization
  DepreciationAmortizationAndAccretionNet
  Depreciation
  AmortizationOfIntangibleAssets
```

Mapping note:

`NetIncomeLoss -> net_income` and `ProfitLoss -> net_income` are intentional.
The internal `net_income` metric represents bottom-line income or loss for the
period. Positive values mean net income/profit, and negative values mean net
loss. Do not create a separate `net_loss` metric unless a later report shows a
different SEC concept with a different business meaning.

Industry target bundles contain only additional industry-specific XBRL concepts
beyond common base concepts. Do not repeat common base concepts inside an
industry bundle. If a common base concept is especially important for an
industry, record that later as metadata such as `important_for_labels` instead
of duplicating the XBRL concept in the industry bundle.

The catalog should be refined from real filing evidence:

```text
MS200 report evidence
  -> missing target XBRL concepts
  -> found but unmapped target XBRL concepts
  -> unknown observed XBRL concepts
  -> reviewed update to mapping_catalog.py or xbrl_direct_candidate_mapping.txt
  -> regression test in tests/test_mapping_catalog.py
```

Target Candidate Embedding Requirement

Plan 201 must align with the XBRL concept mapping pipeline:

```text
company filing
  -> ingest broad XBRL raw facts
  -> classify company industry labels from latest 10-K Item 1 Business
  -> choose common + industry-specific target XBRL concept candidates
  -> Round 1: hard mapping
  -> Round 2: semantic mapping only for missing target XBRL concepts
```

Round 1 hard mapping:

```text
candidate XBRL concept names from the catalog
  compared directly against
observed company XBRL concept names

if candidate concept is observed and approved:
  map raw fact into system financial_metrics

if no candidate concept is observed for the target:
  mark the target XBRL concept as missing for Round 2
```

Round 2 semantic mapping:

```text
missing target XBRL concepts
  -> select their pre-embedded candidate XBRL concept vectors

unknown / unmapped company XBRL concepts
  -> embed during ingestion or experiment run

semantic similarity
  -> compare company unknown concept vectors against selected target candidate vectors
  -> persist review-only mapping candidates
  -> do not automatically promote candidates into financial_metrics
```

The important vector rule:

```text
Target candidate XBRL concept vectors are pre-embedded and reused.
Company-provided unknown XBRL concept vectors are generated when needed.
```

Do not create one blended vector per internal metric. Each system financial
metric can have multiple candidate XBRL concept names, and each candidate XBRL
concept name should have its own vector.

Example:

```text
target metric: revenue

candidate XBRL concept vectors:
  RevenueFromContractWithCustomerExcludingAssessedTax
  Revenues
  SalesRevenueNet

company unknown XBRL concept vectors:
  generated from the company's unmapped XBRL concept name, label, and description
```

Recommended cache key shape:

```text
taxonomy
raw_concept
internal_metric_name
statement_type
industry_label
embedding_model
candidate_text_sha256
catalog_version
```

This keeps semantic mapping aligned with the diagram:

```text
Round 1 answers:
  did we find any known candidate concept name for this target XBRL concept?

Round 2 answers:
  if not, is any unknown company XBRL concept semantically close to one of the
  pre-embedded candidate names for that missing target XBRL concept?
```

Current System Facts

The current system already has the right foundation:

- `src/ingestion/company.py` calls `normalize_companyfacts(..., concepts=None,
  forms=None, taxonomies=None)`, so ingestion keeps a broad raw XBRL archive.
- `raw_xbrl_facts` is the source-of-truth archive.
- `src/processing/mapping_catalog.py` owns the executable catalog-backed mapping
  candidates.
- `src/processing/base_metrics.py` maps clean supported raw XBRL facts into
  canonical base metrics using catalog-backed candidates and approved learned
  mappings.
- `financial_metrics` stores mapped base metrics with `raw_fact_id` and
  accession traceability.
- `companies` stores `sic` and `sic_description`, which can be used as one
  optional supporting signal for assigning hard industry labels.
- `company_industry_labels` stores reusable company industry labels, status,
  confidence, evidence, classifier version, and review metadata.
- `src/retrieval/parser.py` already extracts 10-K `Item 1. Business` as the
  `business` section when SEC item headings are detected.
- `src/analyze/industry_classification.py` implements Gemini-backed hard
  industry classification from 10-K Item 1 Business with strict label
  validation and review fallbacks.
- `src/analyze/prompts.py` is the required location for Gemini prompt templates.
- Settings already include `gemini_api_key` and the pinned
  `gemini-2.5-flash` chat model.
- `src/ingestion/company.py` reuses stored Gemini labels for the same source
  10-K accession and reruns classification when a newer 10-K accession becomes
  the label evidence source.
- `src/ingestion/company.py` loads the approved company concept profile from
  approved global, industry, and company-scoped learned mappings before
  deterministic metric mapping.
- `src/processing/semantic_mapping.py` embeds target XBRL concept candidates
  separately for missing canonical metrics instead of using one blended vector
  per internal metric.
- The MS200 experiment report already shows hard industry labels, target XBRL
  concept coverage, raw fact mapping coverage, alternate XBRL tags, semantic
  candidates, and unknown XBRL concepts.
- The MS3 indicator engine calculates from stable internal metric names, not
  directly from raw XBRL concepts.

Current Limitations

The current system no longer depends on only a flat global `BASE_METRIC_MAPPINGS`
dictionary. The mapping flow is catalog-backed.

```text
observed XBRL concept
  -> catalog-backed mapping candidate or approved learned mapping
  -> system financial metric
```

Remaining Plan 201 gaps after Steps 1-4 are:

- The MS200 report should make approved company concept profile reuse and
  semantic-discovery skip reasons more visible for human inspection.
- Low-confidence or invalid Gemini classification evidence is currently exposed
  as warnings/fallback behavior; persisting an empty review-needed
  classification event would require a separate review-event store or schema
  change.
- Real-ticker validation should confirm the candidate-level semantic mapping
  output is useful before promoting any new mappings.
- `plan201.txt` should continue avoiding a duplicate full candidate catalog
  because `src/processing/mapping_catalog.py` is the executable source of truth.

Plan Goal

Plan 201 should introduce a hard-industry-label-aware mapping layer between the
broad raw XBRL archive and the base financial metric layer.

The goal is not to map every observed XBRL concept.

The goal is to build an inspectable target mapping catalog and use it to expand
concept-to-metric mappings selectively, based on evidence from actual filings.

Non-Goals

Plan 201 should not:

- limit SEC/companyfacts ingestion to a preset concept list
- treat the approved company concept profile as a raw ingestion filter
- freeze a company concept profile forever without revalidation triggers
- map every unknown XBRL concept
- force a company into only one industry label
- mix segment-level facts into consolidated company indicators
- use Gemini to approve raw XBRL concept-to-financial metric mappings
- use free-form LLM output to control mapping behavior
- calculate derived indicators inside ingestion or base metric mapping
- replace the MS3 indicator engine
- change the financial_metrics schema for industry labels

Shared Understanding

The system should use three separate layers:

```text
raw_xbrl_facts
  broad archive of reported SEC/XBRL facts

company_industry_labels
  approved reusable hard industry labels derived from 10-K Item 1 Business or
  manual/source-controlled review evidence

mapping catalog
  source-controlled target XBRL concepts, candidate XBRL concept names,
  pre-embedded candidate vectors, and approved concept-to-metric candidates

approved company concept profile
  reusable company-specific view of approved XBRL concepts that are allowed to
  populate system financial metrics for this company

financial_metrics
  curated, canonical base metrics used by indicators and analysis
```

Unknown XBRL concepts should not be treated as failures by default.

They should be treated as a review queue:

```text
unknown concept
  -> inspect meaning
  -> decide whether it is useful for a base metric or industry indicator
  -> approve mapping if useful
  -> leave raw if not useful
```

Design Decision 1 - Keep Raw XBRL Ingestion Broad

Ingestion should continue to download and normalize broad companyfacts data.

Reason:

- We need unknown concepts available for future review.
- We should not have to re-download SEC data every time the mapping catalog
  expands.
- A company can report useful facts outside its assigned hard industry labels.

Rule:

```text
Do not use industry target XBRL concept sets as ingestion filters.
Use them as mapping and report coverage targets.
```

Design Decision 3 - Keep Canonical Metric Names Stable

Different XBRL concepts can map to the same internal metric.

Example:

```text
RevenueFromContractWithCustomerExcludingAssessedTax -> revenue
Revenues -> revenue
SalesRevenueNet -> revenue
```

The indicator engine should continue to calculate from stable metric names:

```text
revenue
gross_profit
net_income
total_assets
inventory
operating_cash_flow
capital_expenditure
```

The mapping layer owns XBRL concept variation.
The indicator layer should not need to know every XBRL tag variation.

Design Decision 4 - Use Union Target Sets For Multi-Label Companies

A company may have more than one hard industry label.

Labels should be selected from persisted approved `company_industry_labels`.
Those labels may originate from Gemini classification, source-controlled seed
assignments, or manual review.

Gemini classification rules:

- classify from the latest active 10-K Item 1 Business section
- use only the fixed 11-label set
- return strict JSON
- include evidence quotes and confidence
- approve labels only when confidence and validation pass
- reuse approved labels until a newer 10-K is ingested
- reclassify when a new annual 10-K is ingested

The following signals can support the label decision and explain it in the
report:

- SEC SIC code as supporting evidence
- SIC description
- 10-K Item 1 Business narrative
- observed XBRL concept patterns
- manually approved project configuration
- source-controlled seed assignment
- future segment evidence

For a multi-label company:

```text
target_xbrl_concept_set =
  common base target XBRL concepts
  UNION target XBRL concepts for every assigned hard industry label
```

Important rule:

```text
Union the target XBRL concept expectations.
Do not union numerical values unless the facts are clearly consolidated
company-level facts.
```

Segment-level facts should stay separate unless a formula explicitly says it is
a segment-level indicator.

Design Decision 5 - Add Mapping Priority And Status

The catalog should support priority because multiple concepts can map to the
same internal metric.

Example statuses:

```text

missing_target
found_unmapped

not_applicable
```

This lets the experiment report explain what happened instead of just showing a
large unknown-concepts table.

Design Decision 6 - Expand Concept-To-Metric Mapping Selectively

Yes, the concept-to-metric mapping should expand.

But it should expand selectively.

The process should be:

```text
1. Ingest broad raw XBRL facts.
2. Build the common + approved industry target XBRL concept candidate set.
3. Round 1 hard mapping:
   - compare candidate XBRL concept names directly against observed company XBRL concepts
   - map only approved deterministic candidates into financial_metrics
   - record missing target XBRL concepts
4. Round 2 semantic mapping:
   - load pre-embedded vectors for candidate names belonging to the missing
     target XBRL concepts
   - embed unknown / unmapped company XBRL concepts from the provided company
     facts
   - compare similarity
   - persist review-only mapping candidates
5. Human or governed review approves useful candidate mappings.
6. Preserve source raw fact traceability.
7. Leave non-useful concepts in raw_xbrl_facts only.
```

Do not expand mappings just to reduce the unknown count.

A lower unknown count is not the goal.
Better mapping quality is the goal.

Design Decision 7 - Reuse Approved Company Concept Profiles

Normal post-initialization ingestion should not redo semantic mapping when the
company already has an approved concept profile that still covers the required
target metrics.

Meaning:

```text
approved company concept profile =
  global approved mappings
  + industry approved mappings for the company's approved hard labels
  + company approved mappings for the company's CIK
```

This profile is not a fixed ingestion allowlist. It is a reusable mapping view.
The system should still ingest broad raw facts so future catalog improvements,
new issuer-extension concepts, and unknown concept review remain possible.

First ingestion / first review:

```text
ingest broad raw facts
  -> assign approved hard industry labels
  -> build common + industry target XBRL concept set
  -> run Round 1 hard mapping
  -> run Round 2 semantic discovery only for missing targets
  -> approve/reject candidate mappings
  -> persist approved mappings by proper scope
  -> approved company concept profile becomes available for reuse
```

Later ingestion:

```text
ingest broad raw facts
  -> load approved company concept profile
  -> map observed facts through approved profile into financial_metrics
  -> skip semantic discovery if target coverage remains sufficient
```

Revalidation triggers:

```text
run target coverage / semantic discovery again when:
  - approved hard industry labels change
  - a newer 10-K triggers label reclassification
  - an approved concept disappears from active periods
  - a required indicator input becomes missing
  - a new issuer-extension concept appears for a missing target metric
  - a reviewer rejects or invalidates an existing mapping
  - catalog version or mapping policy changes require review
```

Important:

Do not call this a fixed XBRL concept set for every company. The better term is
`approved company concept profile`, because it is governed mapping state, not a
raw ingestion filter.

Plan 201 Data Flow

```text
company filing ingestion
  -> fetch SEC submissions and companyfacts
  -> download active 10-K / 10-Q filing HTML
  -> normalize broad raw facts
  -> store raw_xbrl_facts

industry label selection
  -> if approved labels exist and latest 10-K accession has not changed:
       reuse labels
     else:
       extract latest 10-K Item 1 Business
       classify with Gemini using fixed 11-label set
       validate strict JSON output
       persist approved labels or review-needed evidence
       if refresh fails and prior approved labels exist:
         keep prior labels for continuity and report stale-label review state

target XBRL concept selection
  -> common base targets
  -> UNION industry targets for every approved label
  -> select candidate XBRL concept names

Round 1 hard mapping
  -> load approved company concept profile when available
  -> compare approved candidate XBRL concept names against observed company XBRL concepts
  -> map only approved deterministic candidates into financial_metrics
  -> record missing target XBRL concepts

Round 2 semantic mapping
  -> load pre-embedded target candidate vectors for missing target XBRL concepts
  -> embed unknown / unmapped company XBRL concepts
  -> compare semantic similarity
  -> persist review-only mapping candidates

profile reuse
  -> after review, persist approved global / industry / company mappings
  -> later ingestions reuse the approved company concept profile first
  -> skip semantic discovery unless profile coverage breaks or labels change

analysis readiness
  -> report mapping coverage
  -> calculate indicators from financial_metrics
```

Risks And Mitigations

Risk:
  The mapping catalog becomes too large or too subjective.

Mitigation:
  Add concepts only when a report shows they are useful for a base metric or
  industry-label-specific indicator.

Risk:
  Multi-label union sets create noise.

Mitigation:
  Mark target XBRL concepts as required, optional, core, or specialized. Do not
  treat all target XBRL concepts as mandatory.

Risk:
  Segment-level facts get mixed into consolidated indicators.

Mitigation:
  Add `consolidated_or_segment` metadata and skip segment-only facts for
  company-level metrics.

Risk:
  Indicator formulas become polluted with raw XBRL tags.

Mitigation:
  Keep XBRL concept handling in `src/processing/`. Indicators should use stable
  internal metric names only.

Risk:
  Unknown concept count remains high and looks like failure.

Mitigation:
  Explain in the report that unknown concepts are raw evidence and review
  candidates, not automatically missing mappings.

Risk:
  Gemini misclassifies the company and selects the wrong industry target raw
  fact set.

Mitigation:
  Require strict JSON, validate labels against the fixed label set, require
  confidence and Item 1 Business evidence quotes, and report low-confidence
  classifications as `needs_label_review` instead of using them.

Risk:
  Approved labels become stale after the company changes business direction.

Mitigation:
  Reuse labels during the same annual filing cycle, but trigger
  reclassification when a newer 10-K is ingested. Store source accession,
  filing date, classifier version, prompt version, and Item 1 source hash with
  label evidence.

Risk:
  Semantic mapping candidates are mistaken for approved mappings.

Mitigation:
  Persist semantic matches as review-only candidates. They must not populate
  `financial_metrics` until a deterministic catalog mapping or governed
  approved mapping record exists.

Risk:
  The approved company concept profile becomes stale and hides better new
  concepts.

Mitigation:
  Keep raw ingestion broad, report profile coverage, and rerun discovery when
  labels change, approved concepts disappear, required indicator inputs become
  missing, extension concepts appear for missing targets, or a reviewer
  invalidates a mapping.
